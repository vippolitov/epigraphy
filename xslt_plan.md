# План внедрения XSLT для EpiDoc (Symfony + Twig + текущий JS)

## Цель

Перевести отображение EpiDoc с клиентского ad-hoc JS-парсинга на корректный серверный рендер через XSLT (EpiDoc Reference Stylesheets), при этом:

- не ломать текущую страницу надписи;
- сохранить/переиспользовать текущий UI (переключатели, интерактивность);
- оставить возможность внедрить кастомную систему Зализняка;
- внедрять поэтапно с fallback на текущий рендер.

## Что есть сейчас (кратко)

Текущий поток для страницы надписи:

1. Symfony получает запрос (`/inscription/show/{id}`).
2. Doctrine загружает сущность `Inscription` из БД.
3. Контроллер читает EpiDoc XML из `assets/epidoc/*.xml`.
4. Twig вставляет XML в страницу (`<script id="epidoc-data">`).
5. JS в браузере парсит XML и строит HTML для текста/аппарата/переводов.

Проблема подхода: вся логика EpiDoc/TEI частично реализована вручную на JS, из-за чего легко появляются ошибки на edge-cases (`lb/@break`, `hi/@rend`, spacing между `app`, и т.п.).

## Целевая архитектура

Новый поток:

1. Symfony получает запрос.
2. Doctrine загружает данные надписи из БД.
3. Контроллер читает EpiDoc XML.
4. Серверный сервис `EpidocXsltRenderer` прогоняет XML через XSLT (официальные EpiDoc stylesheets).
5. Сервис возвращает готовые HTML-фрагменты (и позже — данные для интерактивного конструктора чтений).
6. Twig вставляет готовый HTML.
7. JS в браузере отвечает только за интерактивность (toggle, выбор чтений, раскрытие вариантов и т.д.).

## Базовые решения (принять заранее)

### 1) Где исполняется XSLT

На том же сервере, где работает Symfony/PHP, в рамках обычной обработки запроса. Отдельный сервер для XSLT не нужен.

### 2) Какой XSLT-движок

Рекомендовано использовать `Saxon-HE` (через Java), потому что:

- PHP `XSLTProcessor` обычно ограничен XSLT 1.0;
- EpiDoc stylesheets лучше рассчитывать запускать на XSLT 2.0/3.0 совместимом движке.

### 3) Как внедрять систему Зализняка

Поэтапно:

- сначала: XSLT дает корректную базовую разметку/HTML;
- затем: текущий JS/CSS применяет кастомные правила Зализняка поверх семантической разметки;
- позже (опционально): отдельный XSLT-режим/оверрайд для Зализняка.

## Этапы внедрения

## Этап 0. Подготовка и фиксация границ внедрения

Цель: договориться, что именно мигрируем в первую очередь.

Сделать:

- определить MVP: сначала переносим только `edition` (основной текст);
- оставить `apparatus` и `translations` временно на текущем JS-рендере (или подключать позже);
- зафиксировать, что интерактивный конструктор чтений не входит в первый шаг рендера, но архитектурно должен быть поддержан.

Результат:

- понятный scope первого релиза XSLT;
- меньше риск сломать страницу целиком.

## Этап 1. Подключить EpiDoc Reference Stylesheets в проект

Цель: локально иметь официальный набор XSLT, на который будет опираться серверный рендер.

Сделать:

- добавить EpiDoc stylesheets в проект (отдельный каталог, например `tools/epidoc-stylesheets/` или аналогичный);
- зафиксировать источник и версию в документации проекта;
- не смешивать с `vendor/` composer-пакетами (чтобы обновление было контролируемым).

Результат:

- XSLT-шаблоны доступны локально для запуска из приложения.

## Этап 2. Подготовить runtime для XSLT (Saxon-HE)

Цель: обеспечить выполнение XSLT 2.0/3.0 на сервере.

Сделать:

- определить способ запуска `Saxon-HE`:
  - CLI-вызов из PHP (рекомендуемый стартовый вариант);
  - путь к `.jar` через env/config;
- задокументировать зависимости:
  - Java runtime;
  - путь к Saxon;
  - права на запуск процесса;
- определить стратегию обработки ошибок (таймаут, логирование, fallback).

Результат:

- технически готовый движок XSLT для интеграции в Symfony.

## Этап 3. Создать серверный сервис рендера EpiDoc через XSLT

Цель: инкапсулировать XSLT в одном месте, а не размазывать по контроллерам.

Сделать:

- добавить сервис, например `EpidocXsltRenderer`;
- определить интерфейс результата, например:
  - `editionHtml`
  - `apparatusHtml` (позже)
  - `translationsHtml` (позже)
  - `variantModel` (позже, для конструктора чтений)
  - `errors` / `warnings`
- реализовать минимальный метод рендера:
  - принимает XML-строку;
  - запускает XSLT;
  - возвращает HTML-фрагмент(ы).

Результат:

- отдельная точка интеграции XSLT;
- контроллеры не знают деталей Saxon/XSLT.

## Этап 4. Ввести feature flag / режимы рендера

Цель: внедрять безопасно и иметь быстрый откат.

Сделать:

- добавить конфиг режима рендера EpiDoc (например):
  - `legacy_js`
  - `xslt_mvp`
  - `hybrid`
- использовать env-переменную или параметр Symfony;
- предусмотреть fallback:
  - если XSLT не сработал, страница не должна падать;
  - использовать текущий JS-путь как резервный.

Результат:

- поэтапный rollout без риска полной поломки страницы.

## Этап 5. Встроить XSLT-рендер в `InscriptionController`

Цель: начать формировать EpiDoc HTML на сервере внутри текущего запроса.

Сделать:

- в контроллере после чтения `epidocXml` вызвать `EpidocXsltRenderer`;
- передать в Twig новый объект/массив с отрендеренными XSLT-фрагментами;
- логировать ошибки трансформации;
- при отсутствии XML оставить поведение без изменений.

Результат:

- сервер умеет отдавать готовый EpiDoc HTML вместе с остальными данными страницы.

## Этап 6. Обновить Twig-шаблон для поддержки XSLT-режима (без удаления legacy)

Цель: переключаться между старым и новым способом рендера без рефакторинга всей страницы.

Сделать:

- добавить условную ветку в `templates/site/inscription/show.html.twig`:
  - если пришел `epidocRendered.editionHtml`, вставлять его;
  - иначе использовать текущий контейнер + JS XML-парсер;
- временно сохранить `epidocXml` в шаблоне для fallback/сравнения;
- не удалять старые блоки сразу.

Результат:

- можно переключать рендер через конфиг, не переписывая страницу заново.

## Этап 7. MVP: перенести только `edition` (основной текст)

Цель: получить быстрый выигрыш по корректности на самом важном участке.

Сделать:

- использовать XSLT только для отображения основного текста надписи;
- оставить критический аппарат и переводы на текущем JS-подходе (временно);
- проверить, что корректно обрабатываются базовые TEI/EpiDoc конструкции:
  - `lb` / `lb[@break='no']`
  - `hi[@rend]`
  - `supplied`
  - `unclear`
  - `gap`
  - `app/lem/rdg` (в базовом виде)

Результат:

- частичная миграция уже дает ценность и снижает количество ошибок.

## Этап 8. Подготовить семантические "крючки" для системы Зализняка

Цель: чтобы кастомный клиентский слой работал по структуре, а не по строковым эвристикам.

Сделать:

- убедиться, что XSLT-вывод содержит стабильную разметку для:
  - вариантов чтений (`app`, `lem`, `rdg`);
  - `supplied` с `reason=*`;
  - `unclear`;
  - `gap`;
  - переносов/строк;
- при необходимости добавить тонкий post-processing или XSLT-оверрайд, который проставляет `data-*` и классы для JS.

Результат:

- клиентский код может накладывать Зализняк-правила без повторного TEI-парсинга.

## Этап 9. Реализовать гибридный слой для системы Зализняка (поверх XSLT HTML)

Цель: сохранить ваш кастомный режим без дублирования TEI-логики.

Сделать:

- оставить переключатель "Лейден / Зализняк" на клиенте;
- переписать его так, чтобы он работал с XSLT-HTML (а не с XML);
- применять кастомные правила только к отображению:
  - скобки/маркеры для `supplied`;
  - стиль/маркировка `unclear`;
  - маркер `gap`;
  - подсветка/показ вариантов чтений.

Результат:

- базовая научная корректность идет от XSLT;
- проект-специфичная логика Зализняка остается в вашем UI-слое.

## Этап 10. Добавить модель данных для интерактивного конструктора чтений (опционально, но желательно рано)

Цель: подготовить основу для выбора альтернативных чтений по кнопке.

Сделать:

- определить формат данных для клиента (`variantModel`), например:
  - `appId`
  - `defaultReading` (`lem`)
  - `readings[]` (`rdg`) с HTML/текстом и метаданными (`resp`, label)
  - порядок сегментов в тексте
- решить, как отдавать модель:
  - JSON рядом с HTML;
  - или `data-*` в HTML-разметке;
- обеспечить стабильные ID сегментов/вариантов.

Важно:

- интерактивную сборку текста делать на клиенте (JS);
- XSLT/сервер отвечает за корректную семантическую структуру и подготовку данных.

Результат:

- будущий "конструктор чтений" строится без повторного XML-парсинга в браузере.

## Этап 11. Перенести критический аппарат на XSLT

Цель: убрать сложную ручную обработку `app/lem/rdg` из клиентского XML-парсера.

Сделать:

- определить формат выдачи аппарата:
  - XSLT сразу строит HTML-таблицу;
  - или XSLT строит семантический HTML/JSON, а таблицу собирает клиентский UI;
- сохранить текущие UX-паттерны:
  - hover/expand,
  - подписи источников (`resp`),
  - бейджи и локализация.

Результат:

- аппарат рендерится из надежной TEI/EpiDoc-логики, а не из локальных эвристик.

## Этап 12. Перенести переводы и дополнительные EpiDoc-блоки

Цель: выровнять весь EpiDoc-рендер под единый серверный источник.

Сделать:

- переводы (`div type='translation'`) отдавать из XSLT (или через подготовленную модель);
- при необходимости сервером резолвить `resp` через bibliography map;
- унифицировать разметку для фронтового UI.

Результат:

- единый подход к рендеру текста, аппарата и переводов.

## Этап 13. Кэширование XSLT-результатов

Цель: избежать лишних трансформаций на каждый запрос.

Сделать:

- кэшировать результат XSLT по ключу:
  - `inscription_id`
  - hash/mtime XML-файла
  - режим рендера (`legacy/xslt/hybrid`)
  - режим системы (`leiden/zaliznyak`) — если когда-нибудь будет серверный вариант Зализняка
  - `locale` (если влияет)
- определить стратегию инвалидирования при изменении XML;
- логировать cache hit/miss на этапе отладки.

Результат:

- быстрый рендер страниц без повторных тяжелых XSLT-запусков.

## Этап 14. Тесты и регрессии (без подготовки новых тестовых XML на этом этапе)

Цель: закрепить поведение и безопасно развивать рендер.

Сделать:

- добавить тесты на XSLT-сервис и интеграцию с контроллером/Twig;
- добавить snapshot/fixture-тесты на тех XML, которые уже есть в проекте;
- добавить проверки на ключевые кейсы (не создавая сейчас новый набор XML-файлов):
  - переносы строк и `break='no'`;
  - `hi rend='superscript'`;
  - `gap`, `unclear`, `supplied`;
  - обработка вариантов чтений и пробелов между сегментами.

Примечание:

- шаг по подготовке отдельного набора тестовых EpiDoc-файлов пропускаем сейчас;
- к нему можно вернуться позже, когда появятся нужные файлы.

Результат:

- контролируемая миграция без "тихих" регрессий.

## Этап 15. Постепенно выключить legacy XML-парсер в браузере

Цель: сократить техдолг и убрать дублирующую логику.

Сделать:

- после стабилизации XSLT-ветки удалить/свернуть части JS, которые:
  - парсят XML через `DOMParser`;
  - вручную интерпретируют EpiDoc/TEI;
- оставить в JS только:
  - UI-интерактивность;
  - переключение режимов отображения;
  - конструктор чтений (если нужен);
  - UX-детали (hover, copy, expand/collapse).

Результат:

- кодовая база проще;
- меньше рисков расхождения между EpiDoc-семантикой и отображением.

## Отдельно: стратегия для интерактивного выбора альтернативных чтений

Для вашей задачи (пользователь нажимает кнопку и собирает текст из конкретных чтений):

- XSLT/сервер должен готовить:
  - правильный HTML;
  - структурированную модель вариантов (`app/lem/rdg`);
- JS в браузере должен:
  - переключать чтения;
  - пересобирать текст по кускам;
  - отображать результат мгновенно.

Почему так:

- интерактивность и множественные комбинации лучше делать на клиенте;
- TEI/EpiDoc-семантику лучше централизовать на сервере/XSLT.

## Что не делаем в первом цикле

- не создаем отдельный сервер/микросервис для XSLT;
- не переписываем весь UI страницы надписи;
- не переносим сразу все EpiDoc-блоки одним большим коммитом;
- не строим сразу отдельный XSLT-режим для Зализняка (это второй этап развития).

## Критерии готовности MVP (минимум)

MVP считаем готовым, когда:

- XSLT-рендер для `edition` работает на сервере;
- включается/выключается конфигом (есть fallback на legacy);
- страница надписи не падает при ошибке XSLT;
- JS продолжает обеспечивать текущую интерактивность UI;
- есть базовые тесты на интеграцию и ключевые кейсы на уже существующих XML.

## Следующий практический шаг (после утверждения плана)

Начать с технического POC:

1. Подключить Saxon-HE и EpiDoc stylesheets.
2. Сделать `EpidocXsltRenderer` с рендером только `edition`.
3. Подключить через feature flag в `InscriptionController`.
